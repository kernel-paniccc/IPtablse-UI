# Соответствие RFC и классов проекта

Документ фиксирует, как типы и контракты из RFC (`iptablse.pdf`, Stage A)
соотносятся с классами в коде. Нужен, чтобы лид и преподаватель видели,
что проект опирается на RFC, а не пишется вслепую.

## Типы данных (RFC Stage A.1)

| Тип в RFC      | Класс в проекте            | Файл                        |
|----------------|----------------------------|-----------------------------|
| `Rule`         | `ProfileRule`              | `src/profilerule.h`         |
| `RuleDraft`    | `ProfileRule`              | `src/profilerule.h`         |
| `OperationResult` | `OperationResult`       | `src/operationresult.h`     |
| `TrafficSample`   | `TrafficSample`         | `src/trafficsample.h`       |
| `RuleSnapshot` | — отложено до Stage C      | (появится с SQLite-логом)   |

> **Почему `Rule` и `RuleDraft` — один тип `ProfileRule`?**
> На этапе MVP набор полей у них совпадает (chain, protocol, port, action),
> поэтому разделять два класса нет смысла. Если в target version появятся
> поля только для черновика (например, «автор», «комментарий»), тип будет
> разведён.

## Коннекторы (RFC Stage A.3)

| Контракт в RFC        | Интерфейс в проекте        | Файл                        |
|-----------------------|----------------------------|-----------------------------|
| iptables-коннектор    | `IptablesConnector`        | `src/iptablesconnector.h`   |
| Traffic-коннектор     | `TrafficConnector`         | `src/trafficconnector.h`    |

UI (`MainWindow`, будущий `ConstructorWidget`) работает **только** через эти
интерфейсы, а не через конкретные `IptablesLoader` / `NetworkMonitor`.
Это выполняет требование RFC Stage B.1 «разнести UI и загрузчик за
интерфейсом коннектора».

## Хранилище

| Что в RFC                          | Что в проекте                                  |
|------------------------------------|------------------------------------------------|
| SQLite-история (Stage C)           | `OperationLog` — появится на неделе 4          |
| Локальный профиль правил (JSON)    | `ProfileStorageJson` — неделя 3                |

RFC не требует JSON-профиля как такового, но он нужен по исходному ТЗ
(«локальный профиль»). JSON и SQLite не конфликтуют: JSON — рабочий профиль,
SQLite — журнал операций.

## Что НЕ входит в MVP (target version)

Прямо из RFC, но отложено по срокам:

- **Stage C.4** — снапшоты «до/после» и компенсирующие операции.
- **Stage D.3** — полноценный helper/IPC (отдельный бинарь под root + протокол).
  В MVP — `QProcess::start("pkexec", {args})` без shell-строки.
- **Stage D.4** — обработка частичного успеха и обнаружение конфликта ruleset
  перед перечитыванием.
- **Stage D.5** — аварийный таймер отката для удалённого SSH.
- Парсинг `iptables-save` с поддержкой quoting/экранирования (Stage B.2) —
  текущий `IptablesLoader` режет по пробелам; ограничение зафиксировано
  в TODO.

Это **не баги**, а осознанный срез объёма. Полный RFC — это 1–2 месяца
работы на команду, а не 4 недели.
